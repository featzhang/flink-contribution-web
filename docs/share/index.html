什么是大数据，什么是数据工程？

🌐大数据 Big Data
  • 单台机器存不下、算不完，必须靠成百上千台机器协同处理的数据
  • 经典 4V：Volume 量大 · Velocity 快 · Variety 多样 · Value 价值稀疏
  • 本质挑战：把"分布式"的复杂度对上层隐藏起来
🛠️数据工程 Data Engineering
  • 把原始数据变成可用数据资产的工程学科
  • 负责：采集 → 存储 → 处理 → 服务，构建数据管道与平台

🧭
一句话区分：数据科学家用数据"建模型、找规律"；数据工程师修"路和仓库"，让数据可靠地流动起来。到了 AI 时代，两者的边界正在快速融合——这正是本次分享的大背景。

01

批处理 vs 流处理

📦批处理 Batch
  • 攒够一大批数据，定时统一处理（如每晚 2 点跑昨天的日志）
  • 吞吐高、实现简单，但延迟以小时计
  • 代表：Hadoop MapReduce、Spark
🌊流处理 Streaming
  • 数据一来就算，持续不断地处理"无界"数据流
  • 延迟以毫秒 / 秒计，适合实时监控、实时决策
  • 代表：Apache Flink、Kafka Streams
核心区别是数据是否有边界：批处理像快递驿站（堆到一定量集中派送），流处理像传送带分拣（一到就立刻处理）
💡
一个类比：批处理像"快递驿站"——包裹堆到一定量集中派送；流处理像"传送带分拣"——包裹一到就立刻处理。本次分享的主角 Flink，就是把 AI 推理搬上这条实时"传送带"。
02

什么是 Apache Flink

一个开源的分布式流处理引擎：把海量实时数据流，分发到成百上千台机器上并行计算，同时保证不丢、不重、可恢复。

🧠状态管理
  • 能"记住"历史（累计计数、窗口聚合）
  • 崩溃后从 Checkpoint 精确恢复
🎯Exactly-Once
  • 每条数据有且仅有一次生效
  • 金融级一致性保证
🔀流批一体
  • 一套代码同时跑实时 & 离线
  • SQL / Java / Python 多种 API
🚀
Flink 2.0（2025.03 发布）是九年来首个大版本，由 165 位贡献者、25 项 FLIP 提案打磨而成。新增分离式状态管理、物化表、流式湖仓，并把 AI 集成列为核心方向——这正是本次分享的舞台。
03

数据管道 / ETL 是什么

数据管道 = 让数据从 A 地流到 B 地，中途做加工。经典缩写 ETL：

E · Extract
抽取
从数据库 / 消息队列 / 数据湖读原始数据
→
T · Transform
转换
清洗、过滤、聚合……本次新增：AI 推理
→
L · Load
加载
写入数据湖 / 特征库 / 下游系统
💡
传统 ETL 的 T 只做"搬运和清洗"。大模型时代，我们希望在 T 这一步直接调用 AI 模型做推理——比如给每条文本打质量分。这就是"Flink for AI"要解决的核心命题。
本次涉及：Pulsar（消息队列/中转）、Iceberg / Hive（数据湖，存海量数据的"大仓库"）。
04

AI 训练 vs 推理 + 名词速查

🏋️训练 Training
  • 用海量数据"喂"出一个模型，算力消耗巨大
  • 类比：让学生上完整个学期的课
⚡推理 Inference
  • 用训好的模型对新数据做预测（打分/分类）
  • 类比：让学生去考试答题——本次主角

🔤 后面会反复出现的名词，先混个脸熟：

🖥️GPU
  • 擅长大规模并行计算的芯片，跑 AI 模型的主力
🐍Python GIL
  • 全局解释器锁：一个进程同一刻只有 1 线程跑 Python，多核用不满
📞gRPC
  • 高性能远程调用协议，Flink 靠它"喊"GPU 服务干活
🧰Triton
  • NVIDIA 的 GPU 推理服务器，业界事实标准
🎯Exactly-Once
  • 每条数据恰好处理一次，不丢不重
📈HPA / AHPA
  • 自动扩缩容：按需增减机器（A=预测式，提前扩）

演进三部曲

先看清痛点，再讲我们怎么踩了两个坑，才走到今天的方案
本章看点
① 三大场景 & 痛点：GPU 5% · 迭代慢 ② Ray → FlinkJar 本地 → FlinkSQL 远程 ③ 一条主线：把推理越做越"解耦"
Reality Check · 实时 AI 现状

三大业务场景，撞上三大痛点

🎯业务场景（价值巨大）
  • 广告实时特征：日均 200 亿+ 事件，在线打分
  • 实时推理：日均 50 亿+ 条语料经大模型入库
  • 实时训练：在线样本拼接入湖，支撑每日迭代
🔥业务痛点（拦路虎）
  • 远程调用性能低：GPU 利用率仅 5%–10%，资源浪费
  • 故障恢复代价大：无 Exactly-Once，重复 3%–5%，恢复 15–30 分钟
  • 运维迭代成本高：模型硬编码，迭代 2–3 天，每周人工重跑

② FlinkJar 本地

阶段一 · Ray 批处理

🏗️架构：Ray 分布式批处理 + Python 脚本调用模型
  • 数据湖读取 → Ray 分配 batch（~5 万条/batch）→ Python 本地调用 GPU 推理 → 回写
✅优点
  • 开发简单，Python 脚本即可上手
  • Ray 原生分布式，横向扩展容易
  • 适合一次性大规模批处理
❌缺点
  • 全量打标 6–8 小时，无法日更
  • 故障恢复粗：整 batch（5万条）重跑，15–30 分钟
  • 无 Exactly-Once，重复 3%–5%；每周人工介入 2–3 次
💡
Ray 是 UC Berkeley 开源的分布式计算框架，AI 圈很流行。但它是"批处理"思路，天生缺乏流式的背压、状态与精确容错——这就是我们要换掉它的原因。
① Ray 批处理
② FlinkJar 本地
③ FlinkSQL 远程

阶段二 · FlinkJar + 本地算子

🏗️架构：Flink Jar 任务 + Python UDF 本地调用模型
  • 模型嵌入 Jar 包 → Python UDF 在 TaskManager 进程内调用 PyTorch/TF
✅优点（相比 Ray）
  • 切到实时流处理，延迟小时级 → 秒级
  • 状态管理 + Checkpoint 容错
  • 流批一体，7×24 长稳运行
❌三大新痛点
  • Python GIL：32 核机器 CPU 利用率仅 ~3%
  • 模型硬编码在 Jar 里，迭代周期 2–3 天
  • 技术栈割裂（Java/Python/C++），联调 3–5 人天
🐍
为什么 GIL 是致命伤？模型和 Flink 跑在同一个 Python 进程里，GIL 导致 32 核只用得上 1 核。想扩吞吐只能堆机器数量——技术上能跑，工程上不可持续。结论：必须把模型"请出去"。
① Ray 批处理
② FlinkJar 本地
③ FlinkSQL 远程

阶段三 · FlinkSQL + 远程算子（当前方案）

核心思路：解耦——Flink 只管数据编排，模型推理交给独立 GPU 集群，两者用 gRPC 远程连接。

✅收益显著
  • 模型迭代 2–3 天 → <1 小时（算法自助发布，热加载）
  • GPU 独立伸缩，利用率 30% → 75%
  • 算子跨任务复用，开发量 -70%；联调 3–5 人天 → 0.5 人天
⚠️但带来新挑战
  • 远程调用引入网络开销与抖动
  • GPU 服务不可靠（超时/OOM），如何保 Exactly-Once？
  • 大模型冷启动慢（40 分钟），被动扩容来不及
👉 第 5 章将逐一拆解这些挑战的解法

解决远程方案的三大挑战：容错 · 弹性伸缩 · 高性能远程调用
本章看点

Reliability · 条级别容错

挑战一：GPU 服务不可靠，如何不丢不重？

难点：批量数据源最小读取粒度是一个 split（几十万条），一次 GPU OOM 可能导致 50 万条重跑。

源数据落 Pulsar → 按 offset 精确续读 → Checkpoint 对齐 → Iceberg 两阶段提交 = 端到端 Exactly-Once（重复率 0%）
维度无 Pulsar 中转有 Pulsar 中转
故障恢复重读 50 万条（整 split）offset 精确续读
恢复时间15–30 分钟< 10 秒
数据重复率3%–5%（At-Least-Once）0%（Exactly-Once）
Elasticity · AHPA

挑战二：大模型冷启动 40 分钟，怎么扩容？

🐢传统 HPA 的问题
  • 响应式：流量来了才扩容
  • 百亿级大模型（13B）冷启动加载 GPU 约 40 分钟
  • 等实例就绪，请求早已超时堆积
🔮AHPA 预测式扩容
  • 基于过去 7 天同时段流量做时序预测
  • 提前 30 分钟扩容 GPU 实例
  • 快扩慢缩：缩容等 15 分钟冷却，避免抖动
基于过去 7 天同时段流量时序预测，AHPA 提前 30min 备好 GPU、快扩慢缩；HPA 响应式扩容始终慢一拍，落在滞后缺口里 → 超时

Performance · 远程调用四板斧

挑战三：远程调用慢，如何做到高吞吐？

单条 RPC：GPU 利用率仅 5–10%、网络开销占 80%+ → 攒批 256–1024 条：吞吐 10x+、GPU 利用率 60%+（GPU 高并行，1 条与 1024 条耗时相近）
📦批量聚合（最核心）
  • 单条 RPC：GPU 利用率仅 5%–10%，网络开销占 80%+
  • 攒批 256–1024 条/次 → 吞吐 10x+，GPU 利用率 → 60%+
⚡异步解耦 AsyncIO
  • 同步调用时 Flink 线程阻塞等 GPU（P99~50ms），CPU 空转
  • 异步发射，线程继续干活 → 单 TM 吞吐 3x
🔗连接管理
  • gRPC 长连接池（8 连接/TM）+ 健康检查 + 自动重连
  • 连接开销 降低 95%
🛡️容错机制
  • 指数退避重试（≤3 次）+ 熔断（错误率>5% 降级）+ DLQ
  • 成功率 99.9% → 99.99%
💡
为什么批量对 GPU 特别有效？ GPU 高度并行——处理 1 条和 1024 条的计算时间差不多，但通信/调度开销是固定的。批量越大，边际成本越低。这是 GPU 推理区别于 CPU 的本质特性。
